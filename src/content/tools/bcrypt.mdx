        Is bcrypt still a good choice in 2026?

## What bcrypt does

It runs Blowfish's key schedule an absurd number of times. That is the whole idea, and it was a
genuinely new one in 1999.

Blowfish is unusual among block ciphers in that setting up a key is expensive: it derives 4 KiB
of subkeys — the P-array and four S-boxes — by encrypting with the state it is in the middle of
building. bcrypt takes that expensive setup and repeats it 2^cost times, alternating the
password and the salt. The result encrypts a fixed string 64 times, and 23 of the resulting
bytes are the hash.

## The cost parameter, and why it was the point

The paper's title says "future-adaptable", and that is what bcrypt introduced. Every earlier
password scheme had a fixed cost baked in; when hardware got faster, the scheme got weaker and
there was nothing to do about it.

bcrypt put the cost in the hash. A stored `$2a$10$…` says how much work made it, so raising the
cost to 12 tomorrow leaves yesterday's hashes verifying correctly at 10, and each user's hash
can be upgraded silently the next time they log in. Every modern password format copied this.

## The 72-byte limit, concretely

The key schedule cycles through the password bytes, and reads at most 72 of them plus a
terminating null. Try it above: a 72-character password and the same password with anything
appended produce the same hash.

This matters when pre-hashing. A common pattern is `bcrypt(base64(sha256(password)))` to get
around the limit — the Base64 is not decoration, it is there because raw SHA-256 output
contains null bytes, and a null inside the password terminates the key early in some
implementations. Get it wrong and you have silently reduced the password to whatever preceded
the first zero byte.

## Reading the output

```
$2a$10$N9qo8uLOickgx2ZMRZoMye  IjZAgcfl7p92ldGxad68LJZdL17lhWy
└┬┘ └┬┘ └──────── 22 ────────┘ └──────────── 31 ────────────┘
 │   │            salt                      digest
 │   └── cost: 2^10 = 1024 rounds
 └────── version
```

Salt and digest are encoded with bcrypt's own base64 alphabet, which starts `./ABC` rather than
`ABCD` — a small incompatibility that has confused a great many people trying to decode these
by hand.

The whole string goes in the database. It is self-describing, so verification needs nothing
else.

## How this page was verified

bcrypt is not in `@noble/hashes` and there is no Blowfish in any browser, so this is
hand-written from the specification — the only such implementation on the site so far. Three
things check it: the published OpenBSD test vectors, including the ones designed to catch
truncation bugs; parity with Bouncy Castle and with the Rust-backed Python `bcrypt` module; and
a test that recomputes the hexadecimal digits of pi and compares them against every one of the
1042 constants Blowfish's initial state is made of.
