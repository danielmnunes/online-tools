    a: >-

    a: >-

## Checking a bcrypt hash

Paste the stored `$2a$…` string, type the password, press the button. The cost and salt come
out of the string, so nothing else needs setting.

The work runs off the main thread, which matters at cost 14 and above where a single check can
take several seconds in JavaScript.

## What the answer means

**Match** means this password, run through bcrypt with the salt and cost embedded in that
string, produces exactly those 23 bytes. There is no other password known to do that.

**No match** means it does not — and for bcrypt, unlike the raw-digest cases elsewhere in this
category, there is nothing else it could mean. The parameters came from the hash, so they
cannot be wrong.

The only genuine ambiguity is encoding: a password with non-ASCII characters must be given to
the tool as the same bytes the original system used. Almost everything modern uses UTF-8, which
is the default here.

## Reading the cost as an audit signal

The result line names the cost it used. Some rough guidance for a stored hash you have just
found:

- **4 to 7** — a test fixture, or something very old. Not a defence.
- **8 to 9** — was reasonable in 2010.
- **10 to 12** — the current sensible band for a web login.
- **13 and up** — deliberate, and someone has thought about it.

If a production database is full of cost-8 hashes, the fix is to raise the cost in the
application and re-hash each password at next login. You cannot upgrade a stored hash without
the password, which is exactly the property you wanted.

## Comparing in your own code

Use the library's own verify function — `bcrypt.checkpw`, `BCrypt.checkpw`, `password_verify`.
Do not re-derive and compare with `==`: a string comparison that stops at the first difference
leaks how far it got, and the library's version does not.
