## What ParallelHashXOF256 does

Splits the message into B-byte blocks, hashes each to 64 bytes with cSHAKE256, hashes the
collected results together with the block count, and then squeezes as many output bytes as you
ask for. Security strength is 256 bits; the default output is 64 bytes.

## Two levels of parameterisation

ParallelHash is the most heavily parameterised function in SP 800-185, and it is worth listing
what actually affects the value:

| Parameter | Affects the digest? | Recoverable from it? |
|---|---|---|
| Message | yes | no |
| Block size B | yes | no |
| Customization string S | yes | no |
| Output length L | no, for the XOF form | — |
| Number of cores used | no | — |

The last row is the point of the design: parallelism is an implementation choice and does not
show up in the answer. The rows above it are the price — three inputs that must be agreed out
of band.

## Prefix stability, and what it costs

Because L is not encoded, a 32-byte result opens a 64-byte result. That is convenient for key
streams and a hazard anywhere an attacker influences how much digest a verifier expects. The
non-XOF form removes the hazard by committing to the length; prefer it for anything that
functions as a digest.

## The realistic use

Checking a value someone else produced. If a protocol or a native tool computed
ParallelHashXOF256 over some data and you need to confirm it without installing a toolchain,
set the same B and customization string here and compare. Producing such values at volume is a
job for a compiled implementation with cores to use.
