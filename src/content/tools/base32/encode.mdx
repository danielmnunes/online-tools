## Why Base32 exists

Base64 has 64 characters, and four of the reasons it does not travel well are
`+`, `/`, `=` and the distinction between `O` and `0`. Base32 gives up a third of
the density to get an alphabet of uppercase letters and digits only, which means
the same string survives:

- **Case-insensitive systems.** DNS labels, Windows filenames, and anything
  compared after `toLowerCase()`.
- **Human transcription.** No `1`/`l`/`I` and no `0`/`O`, and Crockford's variant
  removes the last of the ambiguity by decoding the confusable letters to the
  digits they look like.
- **Contexts where punctuation is special.** A URL path, a command line, a shell
  variable, an alphanumeric QR code.

The canonical use is a TOTP secret: the string you scan or type into an
authenticator app is Base32, because it has to survive being read by a human,
typed into a phone, and stored by a service that does not know what case it was
in.

## The three alphabets

The RFC 4648 alphabet is `A`–`Z` then `2`–`7`. It is what "Base32" means unless
something says otherwise.

The extended-hex alphabet is `0`–`9` then `A`–`V`, and its one property is that
the *order* is preserved: if byte string A sorts before byte string B, their
encodings sort the same way. Under the standard alphabet they do not, because
digits come after letters there. That matters in systems that store encoded
values as sortable keys.

Crockford's alphabet removes `I`, `L`, `O` and `U` — the last to avoid accidental
obscenities in generated values — and normalises on the way in: decoding is
case-insensitive, `O` and `o` are read as `0`, and `I`, `i`, `L` and `l` are read
as `1`. It has no padding.

## Size and padding

Five bytes in, eight characters out, so Base32 is 60% overhead. The padding at
the end is not data: it records how many bytes were in the final partial group,
and every decoder can work it out from the length. Systems that put Base32 in a
URL usually drop it, and this page decodes either form.
