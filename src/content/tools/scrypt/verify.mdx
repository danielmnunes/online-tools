## Checking a password against an scrypt hash

Paste the stored value and the password, then press the button. A PHC string supplies its own
salt and cost parameters and those win; a bare digest is checked against the fields above. The
result says which was used, so a failure can be diagnosed rather than guessed at.

The work runs in a background thread, so a hash with a large N does not freeze the page.

## Why the parameters travel with the hash

scrypt's output depends on the password, the salt, N, r, p and the length. Five things, four of
them not secret, all of them needed again at verification time.

Keeping them in a constant in the code works until you raise N — at which point every stored
hash was made with the old value and nothing wrote that down. The PHC string exists so each
hash carries its own settings, so old rows keep verifying while new rows get stronger
parameters, and a login can quietly re-hash at the new setting.

## Reading a mismatch

The result line names the parameters the check ran with. A few common cases:

- **Bare digest, wrong length.** If the pasted value is 32 bytes and the field says 64, they
  cannot match. This page uses the pasted value's length, which removes one source of error.
- **Salt encoding.** A salt shown as hex in one system and Base64 in another decodes to
  different bytes if you paste it with the wrong dropdown set.
- **Different function entirely.** An `$argon2id$` string pasted here is rejected with a message
  saying so, rather than failing as a wrong password.

## What a match tells you, and what it does not

A match means the password produces that hash under those parameters. It does not mean the
parameters are adequate. `ln=8` is 256 blocks and about 256 KiB — a value that verifies
instantly and offers roughly nothing against an offline attack. When auditing, read the
parameters as carefully as the result.
