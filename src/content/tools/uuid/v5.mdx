description: >-
  Generate RFC 9562 version 5 UUIDs: SHA-1 of a namespace UUID plus a name, truncated to 128 bits. Deterministic across implementations.
faq:
  - q: >-
      SHA-1 is broken. Why is it here?
    a: >-
      SHA-1 is broken as a collision-resistant hash. Version 5 is not a security protocol; it is a way to mint the same 128 bits from the same name on two machines that will never speak. RFC 9562 still specifies SHA-1 for v5. If you need a name-based identifier and you do not have to interoperate with v5, hash the name with SHA-256 and use the digest itself.
  - q: >-
      Which 128 bits of the SHA-1?
    a: >-
      The leftmost, most significant 16 bytes. The remaining four are discarded. That is appendix A.4 of RFC 9562, not a choice this page made.
  - q: >-
      DNS + www.example.com?
    a: >-
      `2ed6657d-e927-568b-95e1-2665a8aea6a2`. Some older write-ups end in `…a6a4`; that is not the RFC 9562 vector. This page follows the RFC, and the tests re-derive it from SHA-1 of the namespace concatenated with the name.
  - q: >-
      v3 or v5?
    a: >-
      v5, unless you are matching a store of v3 values. The widgets are the same; only the hash function changes.

## A name, hashed with SHA-1

Version 5 is namespace plus name, fed to SHA-1, truncated to 16 bytes, then the version nibble set to 5 and the variant bits set to `10`. The same pair is the same UUID everywhere the RFC is followed.

The name is UTF-8 of what you type. For the DNS namespace that means `www.example.com` as those fifteen bytes, not DNS wire format. Appendix A of RFC 9562 uses that spelling; so does this page.
